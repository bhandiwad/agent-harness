# MCP and isolated execution

## MCP Streamable HTTP

The harness supports fixed remote MCP tools over Streamable HTTP (protocol 2025-06-18 or 2025-11-25). It initializes a session, lists bounded/paginated tool definitions, verifies configured input/output schemas and calls the pinned remote name. JSON and SSE responses are supported. Each call obtains the configured subject's delegated credential. No ambient proxy, redirects, OAuth discovery or automatic write retry is used. Discovery never grants a new tool or permission. Server sampling/elicitation requests and tool-list changes during a call fail closed. Stdio servers, resources, prompts and server-driven background tasks are outside this increment. [MCP transports](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports).

Use `examples/connections.py` to generate example connection records, then replace schemas, endpoint, remote tool name and private delegated-token paths with your server's reviewed contract. Add the local tool name to an agent's `tools` and its permission to Casbin. The per-subject token must target that MCP service, not be a passthrough of an unrelated harness API token.

An MCP write still requires an independent approval. Configure a `receipt_tool` whose input is `{operation_id: string}` and whose output uses the same pinned receipt schema as the write. The harness adds invocation scope and operation/approval identifiers under `_meta["com.pandita/harness"]`; the destination must enforce these semantics and return `{operation_id, status: "confirmed"|"failed", ...}`. MCP itself does not guarantee idempotency or approvals. A lost write result requires receipt reconciliation, never another write. A destination that cannot enforce/resolve these identifiers is unsuitable for consequential tools.

## Shell, Python and browser broker

`pandita-agent-sandbox` is a separately deployed, authenticated **host process**, on a dedicated Linux execution host. It uses an operator-controlled OCI daemon. The API and worker never receive a Docker socket. Prefer a dedicated rootless daemon; access to any daemon is a privileged operator responsibility. Do not point the broker at an application/production deployment daemon.

Each job gets a new non-root container, pinned image digest, read-only root filesystem, no network, no host mounts, dropped capabilities and no-new-privileges. CPU, memory, process, wall-time and output limits apply. Only explicitly named private session text files are copied in through bounded stdin. Only requested bounded UTF-8 outputs are imported back with digest/version checks. No model-selected image, runtime, mount, environment, privilege or network option exists. Input credentials are checked by the broker and never forwarded into the container.

The default runtime is `runsc` (gVisor). Missing runtime or required Landlock support prevents execution. `runc` needs the explicit `allow_standard_runtime: true` lower-assurance setting; it shares the host Linux kernel and is not equivalent to gVisor. There is no automatic fallback. [gVisor architecture](https://gvisor.dev/docs/architecture_guide/intro/).

Landlock is an additional per-process restriction, not a complete sandbox. The launcher requires Linux x86_64/ARM64 and ABI 3 or newer, permits runtime/library reads, and permits writes only under the ephemeral workspace/temp directories (plus device I/O needed by runtimes). It adds supported TCP restrictions and signal/abstract-Unix scoping. The OCI network namespace remains the network boundary. If the deployed gVisor/kernel combination does not implement Landlock, either supply compatible enforcement or deliberately configure `require_landlock: false` after reviewing that runtime's isolation; failure never changes this setting automatically. Seatbelt is macOS-specific and is not part of the Linux deployment. [Landlock documentation](https://docs.kernel.org/userspace-api/landlock.html).

The browser profile uses Playwright in its own image. It executes local HTML/JavaScript and bounded click/fill/text operations with networking denied both by OCI and browser routes. It has no live-site login, web search, downloads or internet browsing. Chromium's inner sandbox is disabled in this profile; the outer OCI/gVisor boundary is required. For hostile workloads use the gVisor deployment and qualify it. Online browsing needs a separately governed egress service and action approvals; adding a URL argument alone is insufficient. Binary screenshots/PDF/image artifacts remain deferred.

## Provision and run

1. Build `sandbox/Dockerfile.code` and `sandbox/Dockerfile.browser` with the sandbox directory as build context. Record the resulting content digests; copy the images onto the dedicated executor. Runtime pulls are disabled. Rebuild and qualify images as part of security maintenance.
2. Copy `config/sandbox.example.json` to the broker host, replace identity/path/image values, and provision the private `state_dir` with mode 0700. Install the standalone package and configure pinned public keys and `config/sandbox-policy.example.csv` with the exact tenant/workspace domain and user subjects. The audience is separate (`pandita-agent-sandbox`). Paths in the broker configuration are absolute.
3. Run `pandita-agent-sandbox --config /etc/pandita/sandbox.json`. The default listener is loopback:8091. Deploy behind authenticated TLS ingress/reverse proxy to reach it from the worker; issue short-lived delegated tokens for this audience. Use one broker process for its private SQLite ledger and bounded admission; do not run multiple replicas sharing that directory. A service supervisor should stop/clean orphaned containers after a broker-host crash using the `com.pandita.sandbox=1` label on the dedicated daemon.
4. Generate the fixed-schema tool records with `examples/connections.py`. Set the broker HTTPS endpoint and subject token files, add tools to the agent, and grant the harness tool permission plus `workspace:read` / `workspace:write` as needed. Broker permissions are separately `sandbox:execute` plus `sandbox:shell`, `sandbox:python` or `sandbox:browser`. Keep tool timeout above broker execution time plus cleanup overhead. No sandbox is enabled by default.
5. Run `AGENT_SANDBOX_TEST_CONFIG=/absolute/test-config.json python -m pytest tests/test_sandbox_linux.py -q` on the target host, with already-built digest-pinned images and a three-second test deadline. This explicit test executes synthetic code in throwaway containers. Other conformance tests use a fake executor and do not prove host isolation.

The broker reserves operation IDs durably before dispatch. Exact repeats return the saved receipt; changed payload/scope under the same ID is rejected. A crash leaves an unknown receipt that cannot redispatch the job. Private artifacts are imported only after a completed validated response and current permissions. Cancelled jobs cannot import artifacts, though a job already accepted by the separate broker may continue until its deadline. Sandbox jobs are configured as private/read effects because they cannot reach external systems; publication remains a separate approved write tool.

Local qualification covers Linux ARM64 on Docker Desktop's standard runtime with Landlock, including actual shell/Python/browser execution and denial/bounds tests. gVisor, Linux x86_64 and customer host deployment remain unqualified. This is not a security audit or an unrestricted internet-browser capability.
